# Learn Loop 规范缺陷修复计划

## 背景

用户在真实使用中发现：模式 A 开场未向用户问询「当前水平」和「目标深度」，执行者自行假设并写入 `run-state.md`（值为「用户未明确说明，按保守假设记录」），且通过了全部机器闸门。

审计后确认这不是孤例，而是两类系统性缺陷的一个实例：

- **根因 1：规范只描述状态，不规定动作和阻塞条件。** 「收集」「确认」「抽查」都是状态词，未规定必须向用户提问、必须等待回答、拿不到时该阻塞还是降级。
- **根因 2：SKILL.md 用「闸门」语气承诺的检查，脚本以字符串存在性实现。** 这类最危险——它给出虚假合规信号，让后续所有人工复核都建立在错误前提上。

修复顺序按此依赖：**先修虚假信号（A）→ 再补交互义务（B）→ 最后统一规格（C/D）**。闸门失效时后面的修复无法验证。

## 通用执行纪律

1. **先写失败测试再改实现。** 每个缺陷先在 `tests/test_learn_loop.py` 加一个能复现该缺陷的用例，确认它 FAIL，再改代码让它 PASS。
2. **闸门必须被验证为「能抓到」，而不只是「能通过」。** 这是本次修复的核心教训：既有闸门全部「通过」，但抓不到真缺陷。每条新闸门都要有正例（合规样本通过）和反例（缺陷样本被拦）两个测试。
3. **每组改完跑一次全量** `poetry run pytest tests/test_learn_loop.py`，16 个既有用例必须保持通过。
4. 不做本计划外的重构、改名、格式整理。

## A 组 · 修复给出虚假信号的闸门（最高优先）

### A1 · `is_sentinel` 漏判嵌套占位值

- **位置**：`scripts/validate_stage.py:96-100`
- **现状**：`is_sentinel` 用 `normalized.startswith(("待填写", "待检索", ...))` 判占位。
- **缺陷**：`templates/01-perspectives.md:16` 的检索记录预填为 `查询词：待填写；渠道：工程博客 / issue / …；命中数：待填写；是否采信：待填写及原因`——以 `查询词：` 开头，**不以「待填写」开头，判为已填**。对照组 `核心立场：待填写，两句话`（第 13 行）正确判空。
- **后果**：这是全套里最危险的一条。未锚定模式下没做过检索，五份记录都是占位骨架，`--stage 1` 却通过 → 执行者据 SKILL.md:17「5 份检索记录完整后才可称领域盲区」认定已完整 → 第 2 步写出「领域盲区：X 无人研究」。**把「我没查」包装成「学界没做过」，并有形式合规背书。**
- **修复思路**：占位判定改为「值内**任意分号/顿号分段**为占位，则整个字段视为未填」。即先按 `；;` 切分，任一段 `startswith` 占位前缀即返回 True。注意保留对整值为空、`—`、`-`、`TBD` 的既有判定。
- **验证**：
  - 反例：`templates/01-perspectives.md` 原样作为第 1 步产物时，`--stage 1` 必须 FAIL 并明确指出检索记录未填。
  - 正例：填入真实查询词/命中数后必须 PASS。
  - 回归：`test_all_validator_accepts_a_complete_mode_a_fixture` 里的完整 fixture 仍需 PASS。若它恰好用了嵌套占位值，说明 fixture 本身不合格，**修 fixture 而非放宽闸门**。

### A2 · 「前 3 不放模型先验」只拦诚实标注

- **位置**：`scripts/validate_stage.py:212-214`
- **现状**：仅检查前 3 个关键发现段落中是否出现字符串 `模型先验·待验证`。
- **缺陷**：产生**反向激励**。全 C 级发现只要不写标签就畅通；写了标签的反被拦。SKILL.md:16/54 承诺的是实质闸门，实现的是字面量匹配。
- **修复思路**：改为按内容判定——前 3 条发现中，任一条的 `来源等级` 字段若不含 `A` 或 `B`，即违规。这与不变量 4「至少一条为 A/B 才写独立共识」的语义对齐，且不依赖执行者自愿贴标签。保留原字面量检查作为附加条件。
- **验证**：构造前 3 条全 `C` 且不含标签的 `03-brief.md`，`--stage 3` 必须 FAIL。

### A3 · 开场画像字段「非空即通过」

- **位置**：`scripts/validate_stage.py:144-147`
- **现状**：`require_nonempty_fields` 检查 `当前水平`、`目标深度`、`角色 / 使用场景`、`画像句` 非空。
- **缺陷**：本次真实产物填的是「有点基础（用户未明确说明，按保守假设记录）」——**非空，通过**。闸门无法区分「用户回答的」和「模型假设的」。
- **修复思路**：为这三个字段增加「来源标记」要求。字段值须以 `用户回答：` 或 `未提供` 之一开头（具体措辞由执行者与 B1 的模板改动保持一致）。`未提供` 时必须同时存在「阻塞说明」或「已按默认值执行」的显式声明。**注意**：这是结构闸门，仍无法验证「用户回答：」后面的内容是否真为用户所说——该语义闸门归入 B3 的人工复核清单，需在 SKILL.md 中明示脚本不负责此项。
- **验证**：本次真实的 `run-state.md`（复制到临时目录）必须 FAIL。

## B 组 · 补齐交互义务与阻塞条件

### B1 · 开场调查必须实际问询（用户发现的原始问题）

- **位置**：`SKILL.md:43-47`
- **现状**：「只在开场收集一次信息：1. 当前水平和目标深度…… 2. 角色和使用场景（开场已提供则记录"用户开场已提供"）。」
- **缺陷**：三处诱导跳过——(a)「收集」未规定必须提问并等待；(b) 未定义信息缺失时阻塞还是假设；(c)「开场已提供则记录」暗示可自行判定已提供。
- **修复思路**：改写为明确的动作+阻塞规范：
  - 必须在执行第 1 步**之前**向用户提问，并**等待用户回答后**才继续；不得以任何默认值替代提问。
  - 仅当用户在开场消息中**已显式陈述**该项时，才可标记「用户开场已提供」并**引用其原话**；模型的推断不算已提供。
  - 用户明确表示「你看着办」时，记为 `未提供`，采用默认值，并在 `run-state.md` 与 HTML 学习画像处**同时**显示该项为默认值。
  - 与 A3 的字段格式对齐。
- **同步改动**：`templates/run-state.md` 的画像字段格式。

### B2 · `{{水平}}`/`{{目标}}` 的实际归属

- **位置**：`SKILL.md:19`、`reference/original-prompts.md:3`
- **现状**：两处都声明「只替换 `{{主题}}`、`{{角色}}`、`{{水平}}`、`{{目标}}`」。
- **实测**：`original-prompts.md` 十段正文中只出现 `{{主题}}`（13 处）和 `{{角色}}`（1 处）。`{{水平}}` 仅在 `reference/curriculum.md:20` 被引用为「依据 `{{水平}}` 指出当前所在级」，`{{目标}}` **全仓库无任何消费者**。
- **缺陷**：规范宣告了四个槽位，其中一个从不被使用，一个只在纪律层被引用而非法条层。这使「必须收集水平和目标」的动机在执行者看来不成立——**收集了也没地方用**，客观上助长了 B1 的跳过行为。
- **修复思路**：二选一，**由执行者判断后在 PR 说明中陈述理由**：
  - 方案甲（推荐）：保留四槽位声明，但在 `SKILL.md:19` 注明 `{{水平}}`/`{{目标}}` 由纪律层（第 6/7 步）消费而非法条层，并在 `curriculum.md` 中补上 `{{目标}}` 的实际使用点（第 7 步「2 小时核心 20%」应按目标深度调整终局项目）。
  - 方案乙：从声明中移除 `{{目标}}`，只保留三槽位。
  - **不可**直接删除而不处理 `curriculum.md:20` 的既有引用。

### B3 · 「人工抽查」的主体与失败动作未定义

- **位置**：`SKILL.md:18`（不变量 6）、`SKILL.md:89`
- **现状**：「该信任型闸门需人工抽查，脚本只检查结构。」第 89 行又把「语义闸门必须人工复核」写进 LLM 自己的交付前清单。
- **缺陷**：三重——(a)「该」指代不明，整条不变量含三条独立规则；(b)「人工」未定义主体，实际坍缩成「LLM 自查」，而这正是该闸门要防的主体；(c) 抽查失败时该阻塞、改写还是标注，未规定。
- **修复思路**：
  - 拆分不变量 6 为可独立引用的三条子项，明确哪条属信任型（「逐字引用用户原话」）、哪条脚本可部分验证。
  - 明确「人工 = 用户本人或另一名人类复核者，不是执行本 skill 的模型」。
  - 规定模型在交付时必须**显式列出**自己无法自证的项，交由用户确认，而不是代为宣告通过。
  - 第 89 行的交付前清单相应区分「脚本已验证」与「需用户确认」两栏。

### B4 · profile 回灌缺少确认动作

- **位置**：`SKILL.md:20`（不变量 8）
- **现状**：「`learner-profile.md` 不记录模型从分数推断的倾向；这类观察只留在本轮产物和复习队列。」
- **缺陷**：(a)「这类观察」外延不明——开场画像来自用户自述，同时符合 `retention.md:15`「用户明确确认的长期事实」和 `templates/learner-profile.md:3`「不要从一次性场景自动填入」两个相反描述；(b) 与 B1 同型，「用户确认的」是状态描述而非动作要求，没有「回灌前必须向用户确认」这一步。
- **修复思路**：明确开场画像默认**不进** profile（属本轮一次性场景）；仅当用户在会话中明确表示「记住这个」时才回灌，且需引用原话。补上确认动作。

## C 组 · 消除三方规格矛盾

以下每条都是 SKILL.md / reference / 脚本对同一字段给出三种规格，执行者按任一方做都会撞另一方。

### C1 · 施考状态行

- **冲突**：`SKILL.md:63` 无条件要求页面显示「交互施考未进行」 / `reference/html-guide.md` 说施考后「可变为」已完成题数 / `scripts/validate_stage.py:519` 用子串 `"交互施考"` 硬查。
- **后果**：按 reference 正确更新状态行会撞闸门，逼人往新状态行里硬塞「交互施考」四字骗过匹配。
- **修复思路**：定义状态行的**两种合法形态**（未进行 / 已完成 N 题），闸门改为「必须匹配其中之一」的正则，三处措辞统一。

### C2 · 施考游标双字段

- **冲突**：`SKILL.md:67/73` 通篇单数「游标」 / `templates/08-exam-record.md:9-10` 有 `已完成题数` 和 `当前游标` 两个字段 / `scripts/validate_stage.py:431` 正则 `(?:当前游标|已完成题数)` 取首个命中，模板顺序下读到的是 `已完成题数`。
- **后果**：两字段可静默漂移。执行者取 `当前游标` 而脚本校验 `已完成题数`，且 `SKILL.md:73` 禁止用聊天记忆纠正，执行者被锁死在错误续考位置。
- **修复思路**：**确定唯一权威字段**（建议 `当前游标`），另一字段要么删除、要么明确为派生展示值并由闸门校验二者一致。SKILL.md 中「游标」一词统一指向该字段名。
- **注意**：`test_exam_cursor_mismatch_is_rejected` 已覆盖此处，改动需保持其通过。

### C3 · 视图层生成事实源内容

- **冲突**：`reference/html-guide.md`「第 10 步快问快答在事实源里若只有题目，须据速查表补出简答」 / `SKILL.md:63`「HTML 是视图，不得成为事实源」 / `reference/retention.md:9`「Markdown 产物集是唯一事实源」。
- **来源**：**此矛盾由上一轮 HTML 改进引入**。当时为修复「快问快答 5 题无答案、无法自测」，选择在 HTML 层补答案，未意识到违反不变量。当前 v2 HTML 中这 5 条答案确实只存在于视图层。
- **修复思路**：答案应补进 `templates/10-cheatsheet.md` 的产物结构与 `reference/retention.md` 的速查表六件套定义（即「快问快答」应包含答案），由事实源向 HTML 单向流动。删除 html-guide.md 中「据速查表补出简答」的授权。
- **注意**：不要求回填既有 `learning/` 产物（探测边界禁止），但需在 `retention.md` 中明确此后新产物的要求。

## D 组 · 默认路径退化（可独立评估）

### D1 · 能力探测默认降级且无人设置环境变量

- **位置**：`SKILL.md:39`、`scripts/preflight.py:172-206`
- **实测**：`verified` 需同时满足「声明变量存在」与「验证变量为真」（`retrieval_declared and env_flag(...)`）。全仓库无任何文件设置或说明谁该设 `LEARN_LOOP_RETRIEVAL_VERIFIED` / `LEARN_LOOP_SUBAGENT_VERIFIED` / `LEARN_LOOP_SUBAGENT_MODE`。干净工作区默认输出 `orchestrated` + `未锚定模式`。
- **缺陷**：与 `SKILL.md:13`「首选 parallel」、`SKILL.md:15`「检索工具不可用时才未锚定」对撞。执行者分叉：老实降级则**默认路径**产出退化为带免责声明的模型先验汇编（不变量 4 使「独立共识」永不可写、不变量 5 使「领域盲区」永不可判）；务实无视则第 39 行形同虚设。
- **附带**（S2）：「未锚定」触发条件在三处不一致——SKILL.md:15 说「工具不可用」，SKILL.md:39 说「未通过验证」，`preflight.py:176` 警告文案说「只有环境声明、未验证」。「工具可用但环境变量没设」这一格（即绝大多数真实运行）归属不明。
- **修复思路**：**此项建议先与用户确认设计意图再动手**，因为它涉及产品决策而非纯缺陷：
  - 选项一：让 preflight 支持由执行者在调用时**显式声明**已实测的能力（如 `--retrieval-verified` 参数），并在 SKILL.md 规定「执行者须先实际试调用一次检索/subagent 工具，再据实声明」。
  - 选项二：将默认值改为「未知」而非「降级」，要求执行者必须显式裁决并记录依据。
  - 无论哪种，需统一 S2 的三处措辞，明确「未声明」≠「不可用」。
